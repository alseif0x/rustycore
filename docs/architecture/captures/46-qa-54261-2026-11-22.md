# Real-client login and live chest recovery on 3.4.3

On 2026-11-22 RustyCore preserved a paid chest across a world-server restart.
Two official clients authenticated with Battle.net and selected the online realm.
Both disconnected before character enumeration. The C++ control reproduced
the disconnect at the same packet.

## Builds and environment

- RustyCore candidate `3708f26e9` on `46-creature-and-loot-recovery`, including the
  accepted server code at `6d2b7dbae`. The aarch64 debug build used
  `cargo build --locked -j1 -p world-server --bin world-server`. Executable SHA-256
  `15a20edcfe5e8368b3ca6c783053ab71f8f7017a6acbfa5b0b93b4d75eb04f98`.
- Two separate copies of the Windows x64 3.4.3.54261 client ran under Wine.
  The executable SHA-256 was `e240f9d88445643d2545ac54b3c3874b2f86336bc8947256584ef07bb5fd66a7`.
  The private QA copy used a cached Blizzard CDN catalogue and its indexes to
  finish startup. The executable and game build key remained those of 54261.
  The DXVK counter showed 59.9–60 FPS at login on the RTX 3070 Ti with Gamescope.
- The test used disposable MariaDB schemas and two QA accounts. A separate
  Battle.net listener served a publicly trusted certificate for the QA DNS name.
  Both accounts authenticated there and saw the online RustyCore realm.
  The bare-IP test also passed OpenSSL certificate verification, but the
  official client disconnected before the realm list.

## Character-entry boundary

Both native client connections reached the Rust candidate at 22:30 UTC.
In order, each received `SMSG_AUTH_CHALLENGE`, sent `CMSG_AUTH_SESSION`,
received `SMSG_ENTER_ENCRYPTED_MODE` and sent `CMSG_LOG_DISCONNECT` with
reason 24. Neither sent `CMSG_ENTER_ENCRYPTED_MODE_ACK` or
`CMSG_ENUM_CHARACTERS`. The two native connections are separate from
the later bot session in the same capture directory.

At 22:43 UTC the same real client selected the same realm through the same
Battle.net listener, with the world endpoint directed to an isolated C++
`worldserver` from the 3.4.3 reference at `a5f8da2eb`. Its PKT contained
the same four opcodes and disconnect reason. The four payload sizes were
49, 73, 65 and 4 bytes respectively, excluding opcodes. The client displayed
`WOW51900319`. PKT SHA-256
`1a4b7cffd341113c24e3268f8fdfb8f883bbb20f22fa29633b04379a917f96f4`.

As an independent serialization check, the compiled C++
`WorldPackets::Auth::EnterEncryptedMode::Write` and the Rust
`sign_enable_encryption` and `EnterEncryptedMode::write` produced identical
packet bodies for two synthetic 16-byte inputs with both values of the
enable flag. The concatenated 260 bytes had SHA-256
`5c3eda6e551a950df5f0a5c07659ee1c5f6ac15cb23c7282b5c526cbb9fcb3c5`.
The reason code and the serialization check leave the client's internal rejection
cause unresolved.

### Independent Battle.net and world control

At 23:06 and 23:13 UTC on November 22, the same 54261 client ran against
both the C++ `bnetserver` and `worldserver` at `a5f8da2eb`. Both processes
used isolated databases and a single QA account joined the realm in each
attempt. The client showed one character beside the online realm. Both joins
ended with the same four opcodes, sizes and reason 24 as the Rust run.
After quitting normally, the client's `Connection.log` recorded a completed
Battle.net login and realm join followed by a world connect and disconnect.
Its native logs supplied no further cause.

For the second join, a volatile database table recorded two digests when
Battle.net wrote the account's 64-byte join key. The verifier reproduced the
native client's 24-byte authentication proof from the first digest and the
two captured challenges. From the second digest it reproduced the 40-byte
session key persisted by the world server. The live 65-byte response passed
independent RFC 8032 Ed25519ctx verification with that session's derived
encryption key and the reference server's public key. Changing the signed
message failed verification. This rules out a mismatched join key in that
attempt. Which server proof the stock client accepts remains unverified.

Private evidence is under `/tmp/rustycore-46-login-native`. The SHA-256 for
the two-attempt `qa46login.pkt` is
`ec8acc71ecaf8a98a740b3830ca5f2af129eb659a60bb75e00d9b624a9bc233b`.
The test restored the QA client configuration and removed the isolated
listeners, databases and volatile digests. The shared services kept running.

### Public endpoint and account provisioning

The client's DNS resolver could not resolve the shared realm's external
hostname. The public Battle.net listeners also presented a certificate that
had expired on November 4. On November 22 at 23:53 UTC the shared realm's
external address was set to its reachable public IPv4 address. Battle.net
was restarted with the valid QA portal name and matching certificate. The
client host verified TLS on ports 1119 and 8081. The shared world process
kept its PID and continued listening on ports 8085 and 8086.

Both services used the same auth database. Realm ID 1 selected build 54261,
and the decoded Win64 seed in `build_info` matched the `Win/x64/WoW` row
in `build_auth_key`. On the public route the real client logged in and the
shared world process authenticated its account. It then received
`CMSG_LOG_DISCONNECT` with reason 24 while waiting for the encryption ACK.

On the isolated Rust candidate, both a fixture game-account name and a
standard Battle.net game-account name produced the same disconnect. A TCP
capture matched both server packet bodies to the application dumps and
recorded the client disconnect before the server's FIN. Sending each
complete frame in one write also produced reason 24. Private evidence is
under `/tmp/rc46-qa-platform`.

The June 26 commit records a successful manual world-entry check with a
54261 client on map 571. The June 28 recordings independently confirm the
client build on both backends. In each recording, the first two little-endian
integers of `CMSG_HOTFIX_REQUEST` are `ClientBuild=54261` and
`DataBuild=51505`, as decoded by C++ `HotfixRequest::Read`. The C++ recorder
header contains 49741. The Rust recording includes the encryption ACK,
character enumeration, player login, world verification and active mover.
[June 26 world-entry validation](https://github.com/alseif0x/rustycore/commit/26595d5543341706024533571d16719062167d85)
and [June 28 C++ and Rust recordings](../../../crates/capture-diff/flows/login/).

On November 23 UTC, both Rust services were rebuilt from the clean June 26
revision with `cargo build --locked -j1 -p bnet-server -p world-server`.
The historical spell loader uses fully qualified hotfix table names, so its
disposable database user received read-only access to six static content
tables. The same 54261 executable and Wine 11 prefix selected the same
online realm using the same canonical game account, ports and private
databases as the November candidate. The June world server authenticated
the account, sent the 65-byte encrypted-mode message and read reason 24.
Both `current.pcap` and `june.pcap` matched the respective backend dumps
for all four handshake frames. Neither run reached character enumeration.

the public network. A client-host TCP trace across ports 1119, 8081, 8085 and
8086 placed the outgoing world disconnect 0.235 ms after the final bytes of
the encryption-mode packet arrived. Battle.net RPC exchanged more data on the
same connection afterwards. The client's own log also placed the world
disconnect before Battle.net began closing. The instance port saw no traffic.

At 00:21 UTC a fresh login to the same Rust world binary (SHA-256
`290353718a1c534b348d03cb082fe203cf2b7ab0e179ef34d8ef4a8933c80fa4`)

### Reproducing the June connection settings

On November 23 the 54261 client on `wowchad` ran directly under Wine. In a
public QA attempt at 00:29 UTC both Battle.net ports negotiated TLS 1.2
ECDHE-RSA with AES-256-GCM. At 00:34 UTC a separate attempt advertised IPv6
in `CMSG_AUTH_SESSION`, matching the June recordings. Both world connections
ended with reason 24 before the encryption ACK.

At 00:42 UTC the same client selected a private build-54261 realm running the
debug candidate `3708f26e9`. A disposable QA account supplied the same game
account ticket as the June Rust recording. All 28 bytes of `CMSG_AUTH_SESSION`
outside the per-session challenge and proof matched June, including the IPv6
flag, region, battlegroup and realm. The server challenge difficulty and the
encryption enable bit also matched. June continued through the ACK to world
entry. This attempt ended with reason 24. The private services, four databases,
database role, port forwards and temporary client profiles were removed.

The older 51943 installation on `wowchad` has a saved Windows shortcut
targeting Arctium Game Launcher. The 54261 QA runs above launched
`WowClassic.exe` directly. The launcher used for the successful June 54261
sessions is absent from the packet recordings.

### Direct launch with a fresh profile

On November 23 the same 54261 executable ran on `wowchad` from a fresh copy
of the game directory, with an empty Wine 10 prefix, empty `Cache` and
`Interface`, and a new `WTF` containing only the portal and display settings.
The run reused the QA installation's game data. After selecting English (US)
and confirming the Americas region, quitting from the login screen saved
`SET portal "US"` over the QA portal. No credentials had been entered.

After restoring the QA portal, the client ran directly under Wine with its
built-in D3D11 on Xvfb. The process could connect only to loopback and the
QA server's public IP. At 01:02:00 UTC the shared Battle.net service logged a
successful login. It handled the realm join at 01:02:03.554. The world service
authenticated the QA account at 01:02:04.288, then received
`CMSG_LOG_DISCONNECT` with reason 24 at 01:02:04.381 while waiting for the
encryption ACK. The client's connection log also recorded login completion,
realm join, world connection and disconnect in that order. Character selection
and world entry remain unverified in this environment.

TrinityCore's August 2024 instructions for `wotlk_classic` (3.4 and later)
specified both the portal setting and a custom launcher. The guide does not
identify a build-specific direct-launch procedure or explain disconnect code 24.
[Historical TrinityCore client setup](https://github.com/TrinityCore/tc-wiki/blob/c9aba256cbec77d8bd95d2d7c5a0b06fac0a7955/install/Client-Setup.md#master-wotlk_classic-wow-34-and-higher-cata_classic-wow-44-and-higher).

### Backend-only encryption control on November 24

The stock client and the reference world server use different public keys
for server authentication. The June Rust revision used the same signing
identity as the reference server.

A temporary world-server candidate (SHA-256
`2bb7fb829e0560572826adffd9756dc4aae803baa9bc404baddca00e777d328b`)
changed only the realm `EnterEncryptedMode` value and signed message from `true`
to `false`. The unmodified 54261 client authenticated to an isolated Rust realm,
selected it and received the four expected handshake opcodes. The enable bit was
zero, but the client again sent `CMSG_LOG_DISCONNECT` reason 24 instead of the
ACK. No character enumeration or player login occurred. The packet files are in
`/tmp/rc46-backend-disabled/packets`; SHA-256 for `EnterEncryptedMode` is
`63c308f958e3bafce7b47795a2f6e0055fbef7cccdbdc655d162e98ce7971086` and for
`LogDisconnect` is
`43ba2fd9f28681b811a7766c427154b0992e15cdefbf0407f7b4bdeac3b9a1b6`.

An independent verifier reproduced the client's authentication proof and derived
the captured session's encryption inputs from the isolated database. The captured
`enabled=false` signature verified under the TrinityCore public key and failed
under the stock public key. Thus the client verifies the server signature even
when encryption is disabled. A backend-only direct-launch fix would require the
private key corresponding to the client's pinned public key; changing the Rust
signature, enable bit, packet layout or realm configuration cannot substitute for
that key. No Arctium process or executable modification was used in this control.

The temporary source change was reverted and the restored world-server rebuilt.
The isolated services, four databases, database role, client configuration and SSH
forwards were removed. The shared services remained active. The four #1342
scenarios still require a client whose trusted server key matches the backend.

| #1342 scenario | Verdict | Last observed step |
| --- | --- | --- |
| Interrupt chase, evade and return home | Not reached | Realm selected. No player entered the map. |
| Observer CREATE and DESTROY across distance and phases | Not reached | Both clients disconnected before character enumeration. |
| Melee and spell start, hit and publication to an observer | Not reached | Neither character could start combat. |
| Transfer and relogin with queued creature effects | Not reached | Neither character could initiate a transfer. |

## Chest 9106001

The integrated test bot exercised the real world socket, two different server
processes and MariaDB 10.11.14. The test placed the existing guarded fixture for
gameobject template 2846 on map 0 with 10 copper and one item 38. Both characters
started with zero money and the disposable database had zero source heads,
bindings and receipts.

| Restart with the window open | `1666644` stopped at 22:31:07 UTC | The instance connection was established at the restart request. The guard verified that the old PID and both listeners were gone. ### November 26 restart on integrated 3.4.3

On native aarch64, the debug world from `b0b974061` and the bot built from
the same revision ran both chest plans against four disposable MariaDB schemas.
Character 15 opened spawn 9106001 (template 2846) with a zero balance. The
first plan saw 10 copper and item 38, the coin removal and the 10-copper
notification. With the loot window open and the instance socket connected,
the harness stopped only the isolated world (PID 2630505). The bot accepted
the expected disconnect and its report passed all three packet expectations.

The replacement world (PID 2631899, same executable) served the second login.
The chest still contained item 38, showed zero copper and returned a zero
payout. The normal loot release completed. All four packet expectations passed.
MariaDB contained one source head, one spent binding and one receipt before
and after the restart. Both character balances stayed at 10 and 0 respectively
through the retry. The receipt recorded only character 15's original payout.

Both `wow-test-bot --cast-lifecycle-plan` processes exited 0. Private reports
are under `/tmp/rc46-observer-qa.0Fn9KdV7`. The SHA-256 of
`loot-1-result.json` is `258b2b907dbdaec6e489f88dffa4aaec3e7fde706f681cefee406126a1a6abac`
and that of `loot-2-result.json` is `f47275210d79e1ee000a05ab07bdebbf28b7b1b9fa6571a1fd1e444af2b1b984`.
An earlier attempt lost the isolated world during login before opening the
chest. The successful pair used a world process detached from the harness
shell and began with zero receipts and zero balances.

After QA, the isolated realm processes stopped and the four cloned schemas
and temporary role were removed. Both shared services retained their original
process IDs.
