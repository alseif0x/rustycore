## Known limit A — conflicting `MAX_SPECIALIZATIONS` and an out-of-bounds default-spec read

**Registered, NOT repaired** (repairing it is a separate authorisation).

- `src/server/game/Miscellaneous/SharedDefines.h:387` declares `constexpr uint8 MAX_SPECIALIZATIONS = 4;`
- `src/server/game/Miscellaneous/SharedDefines.h:984` defines `#define MAX_SPECIALIZATIONS 2`
- The `#define` wins for all code after line 984, which includes `DB2Stores.cpp`.
  Empirical proof: the original `ASSERT(chrSpec->OrderIndex < MAX_SPECIALIZATIONS)` fired at
  `OrderIndex = 2`, which is only possible when the value is 2.
- `SharedDefines.h:986`: `#define INITIAL_SPECIALIZATION_INDEX 4`
- `DB2Stores.cpp:382`: array type `ChrSpecializationByIndexContainer[MAX_CLASSES + 1][MAX_SPECIALIZATIONS]`
  with `MAX_CLASSES = 15` → **`[16][2]`**, 32 pointers, flat indices 0..31.
- `DB2Stores.cpp:1890` `GetDefaultChrSpecializationForClass(c)` →
  `GetChrSpecializationByIndex(c, INITIAL_SPECIALIZATION_INDEX)` → flat index `c*2 + 4` →
  **row `c + 2`, column 0**.
- For every real class (0..12) this is **inside the array but the wrong row**, so it returns
  **another class's specialisation 0** — a non-null pointer, so `ASSERT_NOTNULL` at
  `Player.cpp:28655` does **not** fire and the wrong value propagates **silently**.
  Only class 14 lands past the end (true out-of-bounds).
- Consumers: `Player::GetDefaultSpecId()` (`Player.cpp:28653-28656`), reached from
  `ItemTemplate::IsUsableByLootSpecialization` (`ItemTemplate.cpp:189-198`), which is called by
  `Loot.cpp:120` for **weapons and armour** during loot generation and by
  `Player.cpp:14570` for quest-reward usability.
